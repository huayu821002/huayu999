## 1688 采集器：价格误采集根因定位与修复（commit ae35b74，已部署）

### 背景
崔元峰回传 1688 商品 1053022605528（欧美网纱头饰…，义乌市流雅饰品）的采集诊断：
采出 priceMin=priceMax=wholesalePrice=11，`priceWhy = sku:first(offerList → …)`，
skuPrices 里 5 条全是**别的商品**（亚马逊爆款套装 ¥16.5、欧根纱发箍 ¥12…）。

### 根因（三个叠加）
1. **推荐位被当成 SKU 列表**
   `offerList` / `majorRecommendOfferInfos` / `relationRecommendOfferInfos` / `itemList`
   都是「同店其它商品 / 相似推荐」列表，条目字段是 `offerUrl / offerId / behaviorTag / isCurrentOffer / title`，
   是**商品卡片**不是规格行。旧 `collectSkuEntries()` 只靠「key 名像 sku」或「有 priceText」判定 → 误判。
2. **重放请求污染采集结果**
   诊断里多个 `mtop.1688.mmga.offerdetail.service` 返回 `invalid param` / `{}`：
   1688 的 mtop 接口把 `data` 参数放在 query 尾部，旧的 `replayResources()` 从 performance 拿到的 URL 被
   **截断到 300 字符** → 丢了 `data=` → GET 重放必然 invalid param；
   更糟的是重放走的是被 hook 过的 `window.fetch`，这些垃圾响应又被**当成页面数据存进 STORE**。
   于是真实详情报文始终没拿到，只能落到推荐位价格。
3. **规格名取整段商品标题** → firstSku 变成「欧美网纱头饰羽毛头花欧根纱礼帽头饰赛马会复古走秀花朵发夹发饰」。

### 修复（core 3.2.0 → 3.3.0，采集脚本 2.10.0 → 2.11.0）
- `NOISE_KEY_RE` + `isCardItem()`：推荐容器路径与商品卡片条目一律排除出价格/SKU 提取。
- `collectSkuEntries()` 收紧：必须有真规格字段；`skuSpecOfItem()` 不用超长标题当规格名。
- 新增 `pickCurrentOfferCard()`：无真 SKU 时取 `isCurrentOffer===true` 或 `offerId` 匹配的当前商品价。
- `replayResources()` 改用未挂钩的原始 fetch（`window.__FF1688_ORIG_FETCH__`），URL 不再截断；
  新增 `isUselessPayload()` 过滤 `success:false` / `reason:invalid param` / `data:{}`。
- 新增 `pushRequest()` 记录 mtop 请求的 method+body → `replayCapturedRequests()` 原样 POST 重放。
- 新增 `scanInlineData()`：扫 `__INIT_DATA__` / `__NEXT_DATA__` 等 window 全局 + 内联 script 找首屏详情 JSON。
- `parseLoose()`：兼容 JSONP 包装。
- DOM 兜底：排除推荐卡片价格，支持 `¥9` 单值。
- 诊断新增 `sources` / `apiList` / `payloadTopKeys` / `skuLikePaths`（直接定位真实 SKU 在哪个报文）。

### 测试

## 追加：推送 403 Forbidden 的真实根因（11:02 报障 → 12:15 定位并修复）

### 报障现象
崔元峰在采集面板点推送，得到：
```
状态码: 403
请求地址: https://fiestaflare.com/api/import/1688
返回: Forbidden（403）：这通常说明你装的是旧版脚本（旧版会把请求打到 /api/admin/import/1688，被中间件拦下）。
```
注意：请求地址是**正确**的 `/api/import/1688`，但提示却说「旧版脚本打到了 /api/admin/...」——自相矛盾。

### 排查过程（结论都基于实测，不是推测）
1. **读代码**：`app/api/import/1688/route.ts` 只有 401/200/400/500，**没有 403**；
   `middleware.ts` 只拦 `/api/admin/*` 且返回 `{error:'Forbidden'}` 403。
   → 「请求 /api/import/1688 却拿到 403」在应用层不可能发生。
2. **curl 穷举**：无 Token / 坏 Token / 异常 Origin / Referer / 超大请求体 / `<script>` / `union select` /
   `eval(` / `javascript:` / `../../` / `Bearer` / `x-import-key` / `sign=` 等情形，
   `/api/import/1688` 全部返回 **401**。→ 不是鉴权、不是 CORS、不是这些关键词。
3. **看部署日志**（FTP `/hbuilds/logs/`）：用户报障时间 11:02，线上跑的是 10-23 17:58 那版构建，
   部署本身正常（构建成功、已发布）。→ 排除「部署没生效」。
4. **复现成功**：逐步组合 description 内容后发现，
   当描述里**同时**出现 `<script>` + `union select` + `eval(` + `../` + `javascript:` 时，
   线上返回：
   ```
   HTTP/2 403
   content-type: text/plain
   server: hcdn
   x-hcdn-request-id: ...-phx-edge11
   Forbidden
   ```
   —— **Hostinger 边缘层（hcdn，ModSecurity 异常分）拦的，请求根本没到应用**。
   单独任一特征都放行，多个叠加才触发 → 典型异常分阈值规则。
   1688 商品描述正是从页面整段复制的 HTML，很容易同时含多个特征。

### 附带的诊断缺陷（同样重要）
旧 core 在拿到 403 且响应体含 `Forbidden` 时，**无条件**把响应体改写成
「这通常说明你装的是旧版脚本…」，把服务器真实响应盖掉了。
所以用户看到的「返回」根本不是服务器原文 → 无法定位真实原因。
而且它不看实际失败地址就下「旧版脚本」的结论，与事实矛盾。

### 修复（core 3.4.0/3.5.0，采集脚本 2.12.0 → 2.13.0）
- **诚实诊断**：不再无条件改写 403 响应体，保留服务器原文 + 附加说明；
  只有实际失败地址是 `/api/admin/import/1688` 时才提示旧版脚本。
- **分层判定**：抓 `server` / `x-hcdn-request-id` / `X-FF-Origin` 响应头，区分
  「应用层返回」与「边缘层返回」。
- **服务端标记**：`app/api/import/1688/route.ts` 所有响应加 `X-FF-Origin: app`
  （边缘层不会带这个头，一眼可辨）。
- **消毒**：新增 `sanitizeForWaf()` / `sanitizePayload()`，推送前递归消毒 payload 所有字符串字段：
  script 标签、javascript:/vbscript:、eval(、base64_decode(、document.cookie、
  SQL 注入组合、路径穿越、事件处理属性。
  只针对可疑片段，**正常商品文案与 HTML 一字不改**（13 条真实文案回归验证）。

### 验证
- `public/1688-core.403.test.js`（12 项）：诊断诚实性。
- `public/1688-core.waf.test.js`（11 项）：消毒行为 + 不误伤正常文案。
- `scripts/e2e-waf-matrix.js`：用**构建后的真实 core** 打线上，21 个 WAF 触发样本
  全部穿过边缘层（修复前均 403）→ **0/21 被拦**。
- `scripts/verify-live-waf.js`：直接下载**线上** core 跑同一矩阵 → 0/6 被拦。
- 其余测试：25/25、19/19、12/12、6/6、5/5 全过。

### 教训
- 客户端**不要改写/吞掉服务器原始响应**；出错时保留原文，只在其后追加说明。
- 「同一类特征叠加才触发」的 WAF，必须做组合矩阵才能复现，单特征测试会全部漏掉。
- 区分「应用层 403」和「边缘层 403」的最有效手段：服务端自加一个标记响应头
  （如 `X-FF-Origin: app`），边缘层不会伪造它。
